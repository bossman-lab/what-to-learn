# Agent Launcher — 完整业务与技术方案 v1.0

> 一个运行在现有移动OS之上、取代桌面Launcher、以意图而非App为中心的新一代Agent入口

---

## 一、市场机会与定位

### 1.1 行业背景

移动互联网15年来，用户交互范式从未改变：
- **App网格 → 搜索/点击 → 在App内操作 → 获得结果**
- 每个App是一个孤岛，用户的操作在App之间断裂

2026年，AI Agent能力已初步成熟（Step 3.5 Flash / Claude / GPT-5），但系统的交互范式没有跟上。阶跃星辰做Step AOS（改底层）是大投入、长周期。市场中存在一个明确的**空白生态位**：

> **不改底层OS，用Launcher形态抢占用户意图入口，成为AI Agent时代的"浏览器"。**

### 1.2 市场定位

| 项目 | 描述 |
|------|------|
| **一句话定位** | 让用户从"打开App操作"变成"说一句话拿结果"的智能桌面 |
| **目标用户** | 追求效率的智能手机重度用户（先发）→ 逐步渗透大众C端 |
| **载体** | Android Launcher（替换系统桌面） |
| **竞争壁垒** | 意图理解引擎 + 任务链编排 + 本地语义数据库，非纯UI套壳 |

### 1.3 竞品对比

| | 传统Launcher（Nova/微软桌面） | 系统AI助手（Siri/小爱同学） | Step AOS | **Agent Launcher** |
|--|-----------------------------|--------------------------|----------|-------------------|
| 交互范式 | App网格+图标 | 语音问答 | 智能体重构OS | **意图输入→结果交付** |
| 跨App调度 | ❌ | ❌仅单App | ✅ | **✅** |
| 需改底层OS | ❌ | ❌ | ✅ 需深度定制 | **❌ 运行在Android之上** |
| 开发周期 | - | - | 3-5年 | **6个月MVP** |
| 用户获取成本 | 高（品牌依赖） | 中（预装） | 极高（需硬件绑定） | **中（Play商店上架即用）** |

### 3.2 各层技术选型

| 层 | 组件 | 选型 | 理由 |
|----|------|------|------|
| **UI层** | Launcher前端 | Jetpack Compose（Android） | 原生性能，Material Design 3 |
| **意图引擎** | 本地NLP模型 | Qwen 3.5B / Step 3.5 Flash（工具调用优化） | 轻量，工具调用能力强 |
| **意图引擎** | 云端Complex LLM | GPT-4o / Claude / Step 3.7 Flash | 复杂推理，多轮对话 |
| **编排总线** | DAG调度器 | 自研（参考Temporal轻量版） | 任务链依赖管理+状态持久化 |
| **路由** | Intent三层适配 | Scheme → Android Intent → Accessibility | 覆盖深→广度逐步扩展 |
| **语义数据** | 本地存储 | LanceDB（向量）+ SQLite（结构化） | 端侧推理，不上云 |
| **安全** | 权限沙盒 | Android TEE + 自研权限管理器 | 按任务授予，用完即收 |

### 3.3 三层Intent路由设计

```
意图："帮我订一份XX（外卖）"

Level 1: URL Scheme（覆盖80%高频App）
  → didi://order?addr=xxx
  → meituan://search?keyword=xxx
  → 成功率最高，仅支持已声明的App

  └── 失败则降级 ⬇

Level 2: Android Intent（覆盖15%场景）
  → Intent.ACTION_VIEW + URI
  → 可带数据包，支持部分非声明App

  └── 失败则降级 ⬇

Level 3: Accessibility链（覆盖5%长尾，需要用户授权）
  → 逐屏幕读取UI元素 → 模拟点击
  → 成功率最低，但覆盖面最广
  → 用户需要授权无障碍权限
```

### 3.4 数据流（典型任务 - 订外卖）

```
用户："帮我订一份酸菜鱼"（语音）
  │
  ▼
意图引擎（端侧模型）
  ├─ 识别意图类型：订餐（confidence 0.92）
  ├─ 提取约束：菜品=酸菜鱼，数量=1份，默认地址
  └─ 识别需要补充信息：→ 多轮澄清 "送到家还是公司？"
      │
      ▼（用户响应后）
  ├─ 任务链分解 DAG：
  │   Step1: 打开美团App → 搜索酸菜鱼 → 排序（评分/距离）
  │   Step2: 选择第一家 → 确认订单信息
  │   Step3: 调用支付
  │   Step4: 通知用户结果
  │
  ▼
任务编排总线
  └─ Level 1: URL Scheme → meituan://open?url=...
      ├─ 成功 → 获得返回结果 → 继续下一步
      └─ 失败 → 降级 Level 2 → ...
          └─ 最终失败 → 通过无障碍模式兜底
  
  ▼
结果卡片展示：
  ┌─────────────────────────┐
  │ 🍜 酸菜鱼已下单成功！    │
  │ 商家: XX川菜馆          │
  │ 预计: 35分钟            │
  │ 金额: ¥42.80            │
  │ [查看订单] [再来一单]   │
  └─────────────────────────┘
```

## 四、MVP规划（6个月）

### 4.1 阶段划分

| 阶段 | 时间 | 团队 | 目标 |
|------|------|------|------|
| **Phase 0**：验证与设计 | 第1-2周 | 1人（产品设计） | 完成3条任务链的端到端原型 |
| **Phase 1**：核心引擎 | 第3-8周 | 2-3人 | 意图理解引擎 + 任务编排总线 MVP |
| **Phase 2**：Launcher集成 | 第9-16周 | 2-3人 | 完整Android Launcher + 3条任务链 |
| **Phase 3**：测试与发布 | 第17-24周 | 2-3人 | 内测 → 公开上架Google Play |

### 4.2 MVP功能范围

| 能力 | 范围 | 验收标准 |
|------|------|---------|
| 语义主屏 | 首屏由App图标改为意图卡片流（6张卡片） | 用户打开即可看到"你可能需要的操作" |
| 语音意图输入 | 支持中文/英文语音→文字→意图理解 | 识别准确率>85% |
| 3条任务链 | 外卖（美团）、打车（滴滴）、日历/闹钟（系统） | 零操作完成率>60% |
| 任务预览 | 执行前展示完整计划+用户确认按钮 | 看到"我将：1…2…3…" |
| 本地记忆 | 记住常用地址、外卖偏好、闹钟时间 | 第二次执行无需重复输入 |
| 结果卡片 | 结构化结果展示（非简单的文字回复） | 包含操作按钮 |

### 4.3 技术栈

| 模块 | 技术 | 备注 |
|------|------|------|
| Launcher | Jetpack Compose (Android) | 替换系统桌面 |
| 端侧模型 | Qwen 3.5B / Step 3.5 Flash | 量化4bit，<2GB VRAM |
| 云端推理 | 任意兼容OpenAI API的模型 | 复杂意图fallback |
| 向量数据库 | LanceDB | 本地，无需服务端进程 |
| 意图路由 | 自研规则引擎+LLM fallback | 规则优先，LLM兜底 |
| 任务编排 | 自研DAG调度器 | 参考Temporal设计模式 |
| 开发语言 | Kotlin + Python（后端） | Kotlin for Android，Python for API |

## 五、生态策略

### 5.1 开发者入驻协议（Agent Manifest）

```yaml
# 开发者注册Agent的标准声明文件
agent:
  id: meituan-food-order
  name: 美团外卖下单
  developer: 美团（或第三方适配方）
  
  capabilities:
    - search_food:
        input: { keyword: string, location: string }
        output: [food_item]
    - place_order:
        input: { item_id: string, address: string, payment: token }
        output: { order_id: string, eta: int }
  
  integration:
    level_1_scheme: meituan://open?url={encoded_url}
    level_2_intent: action=VIEW&data={uri}
    auth_required: true
  
  revenue_share: 15%  # Agent Launcher抽成
```

### 5.2 能力市场的冷启动策略

不依赖开发者主动适配，MVP阶段采用**主动适配策略**：
- 团队手动为Top 20 App编写Intent适配规则
- 覆盖用户90%的日常需求（外卖/打车/导航/天气/日历/笔记/搜索/音乐/视频/支付）
- 等DAU破万后，开放开发者入驻入口

## 六、风险与应对

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| Google收紧Accessibility权限 | 高 | 中 | 长期依赖Level 1+Level 2，Accessibility仅作兜底 |
| 用户对"AI接管手机"有隐私顾虑 | 中 | 高 | 全量本地处理、不上云、操作预览+确认机制 |
| App厂商封禁非官方调用 | 中 | 中 | 优先URL Scheme（App官方支持），避免模拟操作 |
| 大模型成本随用户量线性增长 | 高 | 中 | 端侧模型优先，云端仅fallback；模型成本持续下降 |
| 用户换回原生Launcher | 中 | 高 | 提升黏性（记忆层+任务链效率），让"回不去" |

## 七、一句话

> **Agent Launcher不是又一个手机桌面——它是一个在现有OS之上、运行在用户与服务之间的"意图编译器"。** 它的壁垒不在UI交互，而在那个能把模糊意图变成精确任务链的引擎，以及随着使用不断加深的用户语义数据库。6个月、3个人、70万，可以拿到入场券。
