# Jev 技术拆解：当模型放弃"生成"，只做"判断"

> 一个不聊天、不写代码的模型，凭什么比前沿大模型快 193 倍、便宜 444 倍？
> 本文拆解它背后的三个技术核心——尤其是被严重低估的第三个。

---

## 一、一个"反潮流"的模型

2026 年 9 月，一个叫 **Jev** 的模型在开发者社区迅速出圈。上线数日，全球开发者围绕它搭出了 **600 多个开源项目**。

它的"反潮流"之处在于——**它砍掉了大模型最核心的能力**：

| 主流大模型 | Jev |
|-----------|-----|
| 会聊天 | ❌ 不会 |
| 会写长文 | ❌ 不会 |
| 会生成代码 | ❌ 不会 |
| 会做判断 | ✅ **只做这个** |

它的作者是 **Diogo Almeida**——ChatGPT 的联合发明人之一（他参与构建了 RLHF 和 InstructGPT）。

他抛出的问题很尖锐：

> "参与共同发明 ChatGPT 之后，我一直在问自己：**为什么超人级别的聊天模型没有带来 AGI？**"

两年隐身研发后，他给出的答案是：**一套全新的决策模型。**

---

## 二、技术核心一：**不生成，只判断**

Jev 的定义（来自 TypeSafe 官网）：

> **"把非结构化状态输入，输出类型化的概率决策。"**

换成人话：**你给它一段信息，它告诉你答案是什么，以及它有多大把握。**

它**不生成文字**，只做三件事：

| 输出类型 | 功能 | 说明 |
|---------|------|------|
| **Noul** | 是非判断 | 返回 0 到 1 之间的概率，代表某事为真的可能性 |
| **Choice** | 单项选择 | 从预定义列表中选一项，**最多 255 个选项**，适合分类和路由 |
| **Score** | 打分 | 按设定尺度打分，用于衡量紧迫程度、质量或风险 |

**关键设计**：每次回答都**附带完整的概率分布和置信度**。强类型输出——**不需要写 JSON 提示词，不需要额外解析器**。

**为什么这个设计重要？**

传统大模型的输出是**自由文本**，下游系统需要：
1. 写提示词要求它输出 JSON
2. 再写解析器解析
3. 再处理解析失败的情况

Jev 把这三步全部消灭了——**输出即结构，结构即可用**。

---

## 三、技术核心二：**并行采样**（为什么快 193 倍）

这是速度差距的**根本来源**。

| | 生成方式 |
|---|---------|
| **普通大模型** | 一个 token 一个 token 地往外吐，**每个 token 都依赖上一个** |
| **Jev** | **并行采样**——所有输出在一次查询中**同时生成** |

**为什么能并行？**

因为它**不做序列生成**。它的输出是一个**固定结构的判断结果**（一个概率 + 一个选项 + 一个分数），而不是一段可变长度的文本。

**没有序列依赖 → 可以并行 → 一次前向就出结果。**

**性能数据**：

| 指标 | Jev | 前沿大模型 |
|------|-----|-----------|
| 端到端响应 | **70 - 500 毫秒** | 3 秒 - 329 秒 |
| 速度差距 | — | **40 倍 - 200 倍** |
| 输入价格 | **$0.042 / 百万 token** | $0.20 - $10 / 百万 token |
| 输出价格 | **免费** | 按量计费 |

**注意**：193.6 倍 / 444.6 倍是 TypeSafe 在"自动化工作流评测"中的自测数据，官网自己注明"**预计处于实际收益的较高端**"。所以要打折看——但**数量级的差距是真实的**。

---

## 四、技术核心三：**RLCD 校准**（这才是真正的核心）

**速度和价格只是表象。真正的核心是"校准"（calibration）。**

### 4.1 问题：大模型的"过度自信"

现有大语言模型有一个致命缺陷：

> 即使被要求给出置信度，它们也往往**过度自信且不一致**。

TypeSafe 官网的原话一针见血：

> **"如果一个模型能完成某项任务 95% 的时间，但不告诉你它什么时候处于那 5%，它就无法自动化那项任务。"**

**为什么？** 因为自动化系统需要**知道何时该信任模型**：

- 如果它说"我有 80% 把握"，结果实际只有 50%——你**不敢让它自动执行**
- 如果它说"我有 90% 把握"，且实际真有 90%——你**可以放心让它自己做**

**没有校准，就没有自动化。**

### 4.2 解法：RLCD

TypeSafe 为此开发了新训练方法：

> **RLCD**（Reinforcement Learning for Calibrated Decisions，校准决策强化学习）

**目标**：

> **如果模型说某件事有 80% 的概率，那么在它判断为 80% 的那批事情里，最终应该真的有大约 80% 发生。**

**这是一个可验证的数学目标**——不是"感觉更准"，而是**置信度与真实频率的统计对齐**。

### 4.3 校准如何直接变成工程能力

有了校准，系统可以这样分流：

```
置信度 > 90%   →  直接自动执行
置信度 70-90%  →  交给更强的大模型复核
置信度 < 70%   →  转给人来决策
```

**这就是"无人自动化"第一次在工程上可行。**

Earendil 公司 CTO Armin Ronacher 的评价点出了本质：

> "归根结底，这种方式将**幻觉问题的处理责任稍微转移到了用户身上**。用户需要决定：如果这种情况出现的概率只有 50%，那或许可以忽略它。但如果概率达到 95%，那我就可以利用它了。"

---

## 五、为什么"校准"是对 RLHF 的反思

这是整件事最深刻的地方。

Diogo Almeida 把问题**指向了 RLHF 本身**：

> **"为什么今天的大模型总需要有人在回路里？因为训练它的时候，我们字面意义上就把人塞进了那个回路里。"**

拆解一下：

| | RLHF 教给模型的东西 |
|---|-------------------|
| 目标 | **"什么样的回答，人更喜欢？"** |
| 对聊天产品 | ✅ **是优点** |
| 对自动化系统 | ❌ **是致命伤** |

**为什么是致命伤？**

因为"人喜欢"和"校准"是**两个不同的优化目标**：
- **RLHF 优化的是"讨人喜欢"** → 模型学会说漂亮话、给确定性答案
- **校准优化的是"说得准"** → 模型学会诚实地说"我不确定"

**一个为了聊天而训练的模型，天然不适合做无人自动化**——因为它的训练目标里，**埋了一个人**。

**Jev 的本质是一次"目标函数革命"**：从"让人喜欢"，改成"让判断可校准"。

---

## 六、并行判断：一次问十个问题

Jev 还有一个工程上极具价值的特点：

> **同一次请求中的多个问题，共享一份输入，但独立并行评估。**

**实测**（来自公众号"数字生命卡兹克"）：把一条新闻扔进去，同时问——
- 是否 AI 相关？
- 是否广告？
- 是否融资？
- 应归哪个分类？
- 是否值得推送？

**Jev 一口气把全部判断做完，速度不变。**

而传统大模型需要**逐个问题生成回答**，或者把所有问题塞进一个提示词再解析输出。

**这个特性在多问题场景下优势最为明显**——而 Agent 恰恰是"多问题高频"的典型场景。

## 七、开发者已经在用它做什么

| 应用场景 | 效果 |
|---------|------|
| **信息流过滤** | 浏览器插件过滤 X 平台内容，每条判断平均 **380 毫秒** |
| **广告分析** | **40 秒内分析 724 条实时广告，做出 8724 次判断** |
| **浏览器代理** | Browser Use 的 `jev-ultrafast` 项目，用 Jev 做浏览器操作的判断层 |
| **上下文压缩** | 接入 Claude Code，判断哪些上下文关键，实现近乎即时的压缩 |
| **安全分类器** | Vercel 工程师用它替代 ChatGPT Luna 5.6，**速度快 5-18 倍，准确性大幅提升** |
| **邮件分类** | Gemini 准确率略高，但**成本高出 10-20 倍** |
| **营销分析** | 扫描 Meta 广告库，把人工判断**提速 30 倍，成本压到 3 美元以内** |
| **游戏演示** | 玩 Doom：**每秒约 10 次决策**，每小时成本约 7 美元 |

**注意最后一条**：在 Ably Pong 演示中，**Jev 在 12 秒内做出 47 次操作决策，而 Gemini、Claude 和 GPT 在同样时间里只做出两三次。**

**决策频率的量级差**——这才是 Agent 真正需要的。

## 八、局限：**"零幻觉"不等于"永远答对"**

必须泼一盆冷水。

官网写着 **"Zero Hallucinations"（零幻觉）**，这句话很抓眼球，**也很容易被误读**。

TypeSafe 的技术说明给出了准确含义：

> Jev 的输出类型和结构**预先定义**，因此模型**不会产生类型错误**——不会突然跳出指定格式、捏造一个不存在的字段、或在限定选项外随意发挥。

**例如**：程序只允许它在"通过、拒绝、人工复核"三个选项里选，它**不会输出一首诗**，也不会附带一段 Markdown 说明。

**这解决的是"结构可靠性"问题。**

**但它不等于模型不会选错。** TypeSafe 自己的 FAQ 明确承认：

> **Jev"仍然可能出错"。**

**所以正确的理解是**：
- ✅ 它**不会给你格式错误的结果**（结构可靠）
- ✅ 它**会告诉你自己有多不确定**（校准可靠）
- ❌ 它**仍可能判断错**（判断本身有错率）

**校准的价值恰恰在这里**——它让"可能错"变成"**知道什么时候可能错**"。

---

## 九、为什么这件事重要：**自动化 ≠ 协助**

回到 Diogo 的那个追问。他的答案是**一对概念区分**：

| | **协助（Assistance）** | **自动化（Automation）** |
|---|----------------------|----------------------|
| 人在哪 | 坐在屏幕前，AI 干活，**人检查** | **人不在场**，AI 自己判断、自己执行 |
| 需要什么 | 能力够用就行 | **校准 + 结构可靠 + 高频低成本** |
| 现状 | ✅ 已经很成熟 | ❌ 一直做不成 |

> **"今天的 AI 非常擅长协助，但还不擅长自动化。"**

**Jev 的意义**：它第一次把"自动化"所需的三个条件（**校准、结构可靠、高频低成本**）**同时满足了**。

**这就是为什么它火**——不是因为它更聪明，而是因为它**第一次让"无人自动化"变得可工程化**。

---

## 十、结语

> **Jev 的启示不是"小模型打败大模型"，而是"目标函数的革命"。**
>
> - 它放弃**生成**，专攻**判断**
> - 它放弃**讨人喜欢**（RLHF），转向**可校准**（RLCD）
> - 它放弃**通用**，专精**一个环节**
>
> **结果是：它比"更聪明的模型"更有用。**
>
> 而这正是整个 AI 产业当下的缩影——
> **能力跨过了"够用"阈值之后，决定胜负的不再是"多聪明"，而是"多可靠、多便宜、多能落地"。**
