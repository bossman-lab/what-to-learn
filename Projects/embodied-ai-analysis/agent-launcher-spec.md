# Agent Launcher 产品规格书 v1.0

## 一、核心设计原则

| 原则 | 含义 |
|------|------|
| **不造轮子，改造接口** | 不改内核，不重构 App，但重新定义用户↔服务之间的那一层 |
| **意图入口 > 功能入口** | 用户看到的是"我能帮你做什么"，不是 App 图标 |
| **渐进式信任** | 先只读，再调度，再授权——每一步都有用户的显式确认 |
| **结果交付 > 过程操作** | 用户下的是一道指令，不是一串操作步骤 |

---

## 二、六大功能模块

### F1：意图输入层（用户↔Launcher 的界面）

| 子功能 | 说明 | 优先级 |
|--------|------|--------|
| 多模态输入 | 语音+文字+截图/拍照"告诉我要做什么" | P0 |
| 语义主屏 | 首屏不是 App 图标网格，而是**意图卡片流**——高频任务（订外卖、查天气、打车、记笔记）作为卡片直接呈现 | P0 |
| 动态建议 | 基于时间/地点/习惯自动推送意图：_"你通常这个时间叫咖啡，需要吗？"_ | P1 |
| 上下文延续 | 在通知栏/灵动岛常驻当前正在执行的任务状态 | P1 |

**关键区别：** 传统 Launcher 的首屏是"我有什么 App"，Agent Launcher 的首屏是"你现在可能需要什么"。

### F2：意图理解引擎（模糊→精确）

| 子功能 | 说明 | 优先级 |
|--------|------|--------|
| 模糊意图解析 | "帮我安排下周出差"→ 明确约束条件：时间/地点/预算/偏好 | P0 |
| 多轮澄清 | 当意图不够明确时，主动反问而不是强行猜：_"去哪个城市？住几晚？"_ | P0 |
| 任务链分解 | 把"出差"拆成：订机票→订酒店→查天气→打包清单→通知同事 | P0 |
| 冲突检测 | 识别日程/预算/权限冲突并预警 | P1 |

**核心指标：** 用户表达后的"零操作完成率"——用户只说一句话，Launcher 自主完成全链路，不需要用户中间介入。

### F3：跨 App 任务编排总线（核心基础设施）

| 子功能 | 说明 | 优先级 |
|--------|------|--------|
| App 能力注册表 | 每个 App 声明自己能干什么（而不是能打开什么页面） | P0 |
| Intent 路由 | 从"打开美团APP→搜索→筛选→下单"→ 直接调用美团的"下单"能力 | P0 |
| 标准化适配层 | App 级（URL Scheme）→ Activity 级（Android Intent）→ 屏幕级（Accessibility fallback） | P0 |
| 任务状态持久化 | 长任务可中断、可恢复、可回查 | P1 |

**架构要点：** 这不是又一个 App 商店——这是**能力商店**。开发者注册的不是 App，是"原子能力"：搜索、下单、查询、付款、评价……每个能力描述输入/输出/权限需求。

### F4：记忆层（用户模型）

| 子功能 | 说明 | 优先级 |
|--------|------|--------|
| 本地语义数据库 | 用户偏好、习惯、常用地址/联系人/日程，全量本地存储 | P0 |
| 行为模式学习 | 自动学习"什么时候习惯做什么事" | P1 |
| 跨设备同步 | 手机↔手表↔电脑↔车载的无缝状态迁移 | P2 |

**隐私边界：** 记忆数据不上云，端侧加密。需要跨设备同步时，端到端加密传输。

### F5：安全与控制

| 子功能 | 说明 | 优先级 |
|--------|------|--------|
| 任务预览 | 执行前展示完整计划，用户确认后才执行：_"我将：1)订北京到上海机票 2)订外滩附近酒店 3)同步日历，确认？"_ | P0 |
| 操作时间线 | 智能体的每一步操作可回溯查看 | P0 |
| 权限沙盒 | 按任务授予权限，任务完成后即刻回收 | P1 |
| 一键撤回 | 任何误操作可以撤销（像 Gmail 的"发送后撤回"） | P1 |

### F6：交付层（结果交互）

| 子功能 | 说明 | 优先级 |
|--------|------|--------|
| 结果卡片 | 结构化呈现执行结果：航班信息+酒店确认号+天气+待办事项，一张卡片全包 | P0 |
| 渐进式交付 | 长任务先给中间状态，再更新最终结果 | P1 |
| 失败重试 | 某个环节失败时，自动降级或换路径 | P1 |

## 四、三个分层部署方案

### 方案 A：纯 Android Launcher（推荐起手式）

| 项目 | 方案 |
|------|------|
| 实现方式 | Android Launcher App（替换桌面） |
| Intent 机制 | Android Intent + URL Scheme |
| 端侧模型 | 4B 级模型本地推理，复杂意图走云端 |
| 生态依赖 | 零（主动适配主流 App 的 URL Scheme） |
| 开发周期 | 3-4 人 × 6 个月 MVP |

**优势：** 不需要任何厂商合作，不需要改系统，用户下载即用。

**劣势：** 受限于 Android Intent 的能力边界，深度调度需要 Accessibility Service（Google 正在收紧）。

### 方案 B：厂商预装深度版

| 项目 | 方案 |
|------|------|
| 实现方式 | 与手机厂商合作，系统级嵌入 |
| 能力 | 可调用系统 API、通知拦截、快捷设置 |
| 适配深度 | 可做到接近 Step AOS 级别的调度 |
| 开发周期 | 需谈厂商合作，12-18 个月 |

### 方案 C：跨平台 Agent 层（终极形态）

| 项目 | 方案 |
|------|------|
| 实现方式 | 自建轻量运行时，跑在现有 OS 之上 |
| 能力 | 统一调度协议，设备间任务迁移 |
| 类比 | 微信小程序 = 跨平台的 App 层，Agent Launcher = 跨平台的 Agent 层 |
| 开发周期 | 先走方案 A，验证后再扩展 |

## 五、MVP 的最小可行定义（6 个月，3-4 人）

### 必须有的能力

| 能力 | 验收标准 |
|------|---------|
| 语义主屏 | 首屏展示 6 张意图卡片（订外卖/打车/查天气/记笔记/设闹钟/发消息） |
| 语音意图输入 | "帮我订一份xx"→ 自动完成下单全流程 |
| 3 条高频任务链 | 外卖（美团）、打车（滴滴）、闹钟/日历（系统） |
| 任务预览 | 执行前展示完整计划，用户确认后才执行 |
| 本地记忆 | 记住常用地址、外卖偏好、起床时间 |

### 技术栈建议

| 组件 | 选型 |
|------|------|
| 端侧模型 | Step 3.5 Flash / Qwen 3.5B（工具调用能力强） |
| 向量数据库 | LanceDB（本地嵌入，无需服务端） |
| Intent 路由 | 自建规则引擎 + LLM fallback |
| 前端 | Jetpack Compose（Android Launcher） |
| 任务编排 | DAG 调度器（自研，参考 Temporal 的简化版） |

## 六、一句话

> **Agent Launcher 不是"更好的手机桌面"，而是"用户意图和数字服务之间的编译器"。** 它把 "用户想做的事" 编译成 "跨 App 的可执行任务链"——当前这个编译器的正确性只有 70%，但用户容忍度比想象的高，因为"帮我做完 70% 的活"比"打开 App 从零开始"好 10 倍。
